# LumaFiles 内存与缩略图优化方案 v1.1

> 日期：2026-11-23
> 起点：`main` @ `4c3d372`（clippy 基线清理合入后以合入点为准）
> 关系：补充 `docs/prime-files-优化方案.md`。那份讲构建、卡顿和稳定性，**内存几乎没涉及**；本方案只讲内存和缩略图缓存。
> 分工：复查方写规格并复查，DeepSeek 写代码。

---

## 0. 原则

1. **先测再改。** 第 0 项（基线测量）完成之前，不做任何优化。每一项都要在报告里给出改动前后的数字。
2. **不改行为。** 用户看到的界面、搜索结果、排序和配置格式都不变。索引文件格式不变（`PFEVRY03`）。
3. 遵守 `.rules`：不用 unwrap / `let _ =`，不加 `mod.rs`，注释只写为什么。不改 `third_party/gpui`。
4. 新增依赖（例如 mimalloc）必须先经 BoBO 同意。
5. 每一项一个英文提交；合入门槛沿用 `docs/Clippy基线清理-规格.md` §2 的命令。

## 1. 现状（复查方 2026-11-23 读代码和本机文件得出）

### 1.1 全盘文件名索引（`nohrs-pages/src/explorer/everything.rs`）

- 本机快照 `userdata\cache\everything.idx` 有 **261 MB**，2 个分区，第一个分区就有 **185 万条**，两个分区合计约 **370 万条**。
- **只有在不使用索引服务（MFT 服务）时才会加载这份索引。** `ensure()` 里在 `mft::searchable()` 为真时直接返回，注释写明“service 自己保存和搜索文件名，本进程不保留”。外部 Everything 模式同样不加载。所以下面关于索引的几项，只对“自带索引”模式有效。
- 内存里每条 `Entry` 占 **48 字节**（`size` 和 `mask` 两个 u64、5 个 u32、3 个 u16、1 个 u8，对齐后是 48）。每个分区另外存两份字符串：原文 `names` 和小写 `lower`。第一个分区里两者都是 41 MB。
- **估算常驻约 350 MB**：370 万 × 48 B ≈ 178 MB，字符串约 154 MB，另外还有拼音和 `non_ascii`。这是根据结构推算的，以第 0 项的实测为准。
- `load()` 先用 `std::fs::read` 把 **261 MB 一次性读进内存**，再把每一条拷贝成结构体，字符串也用 `to_vec()` 再拷一份。所以**加载时的峰值约是常驻量再加 261 MB**。
- 扫描过程中 `names`、`lower`、`pinyin`、`entries` 都是边扫边 push 的，代码里**没有 `shrink_to_fit`**，容量可能是实际长度的 1–2 倍。

### 1.2 文件列表（`nohrs-pages/src/explorer/state.rs`、`list_setup.rs`）

- 一个文件夹的列表在内存里有 **3 份完整拷贝**：`entries`，`filtered_entries`（`state.rs:1337` 的 `visible.cloned().collect()`），以及列表控件里的那份（`list_setup.rs:18/51` 的 `set_items(self.filtered_entries.clone())`）。
- 每条 `FileEntryDto` 有 3 个 `String`：`name`、`path`，还有 `kind`（只可能是 `"file"`、`"dir"`、`"symlink"`，也是 `String`）。
- 在过滤框里**每按一个键**，都会把通过过滤的条目整份再拷一遍。一个 10 万文件的文件夹，三份拷贝估计要几十 MB，打字时还会明显变慢。

### 1.3 缩略图和图标（`nohrs-pages/src/explorer/thumbnails.rs`）

**已经做好的（不要重复做）**：

| 策略 | 现在的做法 |
|---|---|
| 内存上限 | 每个窗格 192 MB（`READY_BYTES_CAP`，按 RGBA 计），超过后先淘汰最久没上屏的缩略图，降到上限的 3/4 |
| GPU 一起释放 | 淘汰和离开文件夹时都会调 `drop_image`，GPU 图集里的拷贝也一并释放 |
| 滚走就取消 | 已经滚出屏幕、还在排队的请求直接取消 |
| 快慢两条队列 | 2 个快线程只读 Windows 已有的 thumbcache（约 10 ms 一张），4 个慢线程负责现场生成 |
| 磁盘缓存交给系统 | 先用 `SIIGBF_INCACHEONLY` 读 Windows 的 thumbcache，没有才生成；程序自己不建磁盘缓存 |
| 尺寸分档 | 64 / 128 / 256 / 512 四档（`zoom.rs:115`） |
| 放大时先用小图顶着 | 大尺寸还没出来时显示已有的小尺寸 |
| 同类图标共用 | 同扩展名的图标全进程只提取一次，共用一张贴图 |
| 失败重试 | 按 15 秒、1 分钟、4 分钟退避，最多 3 次 |
| 文件变了就失效 | `forget()`（`navigation.rs:437`） |
| 预览不整张解码 | 向 Shell 要合适尺寸的图（`PERFORMANCE.md` §7：48MP 照片 +555 MB → +2 MB） |

**缺口**：

- **上限按窗格算，不是全局的。** 每个 `ExplorerPane` 一份，侧栏 `places.rs` 的图标也是单独一个 `Thumbnails`。双窗格最坏是 2 × 192 MB，GPU 图集里再各一份，**接近 800 MB**。
- **图标不计入上限，也不会被淘汰**（`ready_bytes` 注释写明 “icons are not counted”，淘汰时只处理 `Kind::Thumbnail`）。类型共用的图标没有问题，但文件夹、`.exe`、`.lnk` 是每个路径各一张。在一个有 10 万个子文件夹的目录里从头滚到尾，按 32 px 计每张 4 KB，**离开这个文件夹之前会一直占着约 400 MB**。
- **返回上一个文件夹要全部重新取。** `show_directory()` 一换目录就全部清空。
- **转到后台不释放。** 快速启动让进程常驻（`keep_running` 默认开启），所有窗口都隐藏后，缩略图仍然留在内存和 GPU 里。
- 小问题：超过上限、但屏幕上的图都还在显示时，`begin_frame` 每一帧都会把所有条目扫一遍，并拷贝路径字符串。

### 1.4 日志（`nohrs-core/src/telemetry/logging.rs`）

- 日志按天（UTC）切分，`max_files` 为 `None` 时全部保留，**单个文件没有大小上限**。
- 本机 `userdata\state\logs` 下有 `nohrs.log.2026-11-15` **524 MB**、`11-14` 120 MB、`11-16` 61 MB。这些占的是磁盘，但说明某些天日志写得极多，需要查清楚原因。

## 2. 优化项

优先级：**P0** 低风险、收益明确，先做；**P1** 改动面较大；**P2** 先看基线结果再决定。

| 编号 | 内容 | 优先级 | 预计收益 | 风险 |
|---|---|---|---|---|
| **O0** | 内存基线测量脚本和场景 | P0 | — | 无 |
| **O1** | 索引流式加载 | P0 | 加载峰值约 −260 MB | 低 |
| **O2** | 索引扫描完和加载完后收缩容量 | P0 | 最多回收一倍多余容量 | 很低 |
| **O3** | 缩略图改为全进程共用预算（512 MB） | P0 | 多窗口、多窗格时有上限；单窗格可用更多，滚动更顺 | 低 |
| **O4** | 每路径图标计入预算并参与淘汰 | P0 | 大文件夹省几十到几百 MB | 低 |
| **O5** | 日志单文件和总量上限，并查明 11-15 那天为什么写了 524 MB | P0 | 磁盘 | 低 |
| **O6** | 后台常驻时释放缩略图和预览 | P1 | 后台占用明显下降 | 低 |
| **O7** | 文件列表不再拷三份 | P1 | 大文件夹省几十 MB；过滤时打字更快 | 中 |
| **O8** | 返回上一个文件夹时保留缩略图 | P2 | 体验（不是内存） | 低 |
| **O9** | `Entry` 从 48 字节压到 40 字节 | P2 | 370 万条约 −30 MB | 中 |
| **O10** | 试用 mimalloc | P2 | 看碎片的实测结果 | 新依赖 |

### O0 基线测量
- 新增 `scripts/measure-memory.ps1`：每秒采样指定进程的**私有内存**（`PrivateMemorySize64`）、工作集、句柄数、GDI/USER 对象数，输出 CSV，并给出每个场景的峰值和稳定值。
- 场景，每个跑 3 次取中位数，release 构建，便携模式保持不变：
  1. 冷启动到首帧，空闲 30 秒；
  2. 自带索引模式下，等索引加载完成（记录峰值和稳定值）；
  3. 打开一个 10 万文件的文件夹（用脚本生成测试目录），然后在过滤框里输入 5 个字符；
  4. 网格视图 256 px 档，从头滚到尾一个 1 万张照片的文件夹；
  5. 双窗格两边都做场景 4；
  6. 一个 10 万子文件夹的目录，在列表视图里从头滚到尾；
  7. 关闭所有窗口（进程常驻），等 10 分钟；
  8. 打开、关闭一个大文件夹，重复 10 次，看内存能不能回到原来的水平（判断泄漏和碎片）。
- 结果写进 `docs/PERFORMANCE.md` 新增的 §10“内存”。**之后每一项都用同样的场景对比。**

### O1 索引流式加载
- `load()` 改用 `BufReader`：先读文件头和分区头，按准确长度直接把 `entries`、`names`、`lower` 读进各自预先分配好容量的缓冲区，不再先把整个文件读进内存。
- 字符串直接读进 `Vec<u8>` 再 `String::from_utf8`，不要先切片再 `to_vec()`。
- 校验规则（偏移越界、父条目必须排在前面、末尾必须正好读完）一条都不能少；文件损坏时照样返回 `None`。
- 验收：场景 2 的峰值明显下降；现有的加载测试和损坏文件测试全部通过；新增一个测试，验证“文件末尾多出一个字节”时返回 `None`。

### O2 收缩容量
- 每个分区在扫描完成、加载完成、拼音补全之后调用一次 `shrink_to_fit`（`names`、`lower`、`pinyin`、`entries`、`non_ascii`、`paths`）。
- 不要在扫描过程中收缩（会反复重新分配）。
- 验收：场景 2 的稳定值下降，或者在报告里说明容量本来就接近实际长度。

### O3 缩略图全局预算
- 新增一个全进程共用的“缩略图字节账本”（例如放在 `Service` 里的一个 `AtomicUsize`），所有 `Thumbnails` 实例共享同一个总上限 **512 MB**（BoBO 2026-11-23 确定，见 §5 Q1）。原来每个窗格 192 MB 的单独上限取消，`READY_BYTES_CAP` 改为全局值。
- 超过上限时，每个实例先淘汰自己最久没上屏的；如果还超，下一帧再淘汰。不要求跨实例做严格的全局 LRU。
- 测试仍然可以通过字段设置小上限（沿用 `cap` 字段的做法）。
- **512 MB 带来的变化（BoBO 已知晓）**：现在双窗格合计最多 384 MB（2 × 192），改成全局 512 MB 后，单个窗格最多可以用到 512 MB，滚动大相册时重新加载会更少；O3 的作用变成**给多窗口、多窗格的总量封顶**，而不是降低双窗格的占用。GPU 图集里还有一份拷贝，最坏情况约 1 GB。
- 验收：场景 4 和 5 的缩略图总字节数都不超过 512 MB（在报告里用日志或计数器证明）；现有缩略图测试全部通过。

### O4 图标计入预算
- 每个路径独有的图标（文件夹、`.exe`、`.lnk` 等，也就是没走 `class_icons` 共用的）计入 O3 的预算，并按同样的规则淘汰。
- 共用的类型图标不计入，也不淘汰（它们由 `Service.class_icons` 持有，数量受扩展名种类限制）。
- 淘汰图标只删 slot；**是否调用 `drop_image` 要区分**：共用图标不能 drop（其他行还在用同一张贴图），独有图标要 drop。
- 验收：场景 6 的内存不随滚动无限增长。

### O5 日志上限
- 新增配置项 `[diagnostics] log_max_file_mb`（默认 50）和 `log_max_total_mb`（默认 200），写进 `docs/config.md` 和 schema。超过单文件上限后，当天停止写文件并记一条警告（stderr 照常输出）；启动时总量超过上限就从最旧的文件开始删除。
- **先查原因**：读 `nohrs.log.2026-11-15` 里出现最多的前 20 条消息（按 target 和消息模板统计），写进报告。如果是某处循环打日志，另立一个修复提交。
- 验收：新增测试覆盖单文件上限和启动时清理。

### O6 后台瘦身
- 所有窗口都隐藏（进程常驻）超过 **3 分钟**（BoBO 2026-11-23 确定，见 §5 Q2）后：清空所有 `Thumbnails`（`drop_image`）、清空预览，释放已关闭标签页和不可见窗格里的列表缓存。全盘索引**保留**（重新加载太慢）。
- 窗口再次显示时照常重新取（快通道很快）。
- 不调用 `SetProcessWorkingSetSize` 之类强制把内存换出的 API（只会让下一次显示变慢）。
- 验收：场景 7 的稳定值明显下降；再次显示时没有闪退或空白。

### O7 列表不再拷三份
- `filtered_entries` 改成下标列表 `Vec<u32>`（指向 `entries`），或者 `entries` 改存 `Rc<FileEntryDto>`、三处共享。二选一，由 DeepSeek 评估后在报告里说明理由，**先交方案、经复查方确认后再改**。
- `kind` 改为枚举，或者 `&'static str`（`nohrs-models` 里本来就有 `FileKind`）。如果牵涉面太大，这一点可以单独提交。
- 涉及选择、排序、过滤、树视图（`tree.rs:101`）、搜索（`search.rs:76`）、批量重命名（`preview_state.rs:37`）。现有测试必须全部通过。
- 验收：场景 3 的内存下降；在过滤框里打字时，每个按键的耗时下降（用 tracing span 计时）。

### O8 返回上一个文件夹时保留缩略图（可选）
- `show_directory()` 不再一换目录就清空，而是在 O3 的预算内保留最近 1–2 个目录的缩略图；超出预算时，先淘汰不在当前目录的那些。
- 只在 O3 完成后再做。

### O9 压缩 `Entry`（可选）
- 如果某个分区里每条的 `lower` 偏移都等于 `name` 偏移、`lower_len` 都等于 `name_len`（纯 ASCII 或者小写后长度不变），就把这个分区标记为“同布局”，省掉这两个字段。
- 会改动搜索最核心的路径，必须先用现有 criterion 基准对比搜索速度，变慢超过 5% 就放弃。

### O10 mimalloc（可选，需要 BoBO 同意加依赖）
- 只有在场景 8 显示“关闭大文件夹后内存回不到原来的水平”时才做。用 `#[global_allocator]` 切换后，重跑全部场景对比。

## 4. 不做的事

- 不改索引文件格式，不改 gpui，不改搜索结果和排序。
- 不自建缩略图磁盘缓存（Windows 的 thumbcache 已经够用）。
- 不强制换出工作集。
- 不把全盘索引搬进索引服务（这属于原方案 §5“索引服务”，另立项）。
